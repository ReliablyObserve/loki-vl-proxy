# Known Differences and Known Issues

API inventory is generated from the route and conformance evidence below.

This project is a Loki-compatible read proxy for VictoriaLogs. It is not a claim
that VictoriaLogs is natively Loki or that every Loki behavior is reproduced in
the backend itself. This page tracks the differences, scope boundaries, and
operational caveats that still matter in the current codebase.

## Intentional Scope Boundaries

<!-- api-status:start -->
The proxy serves Loki's read API; write endpoints such as push are not supported (ingest goes to VictoriaLogs directly). Optional deletion management is outside read API scores: its opt-in handler runs Loki's create and cancel as VictoriaLogs delete tasks, and answers Loki's 500 for the list and for queries a VictoriaLogs filter cannot select. The alerting-rules read API remains in scope, including `/api/prom/rules*` for vmalert. The deprecated read aliases `/api/prom/label`, `/api/prom/label/{name}/values`, `/api/prom/query`, `/api/prom/series` and `/api/prom/tail` are unsupported and excluded from totals, gaps and compatibility scores (owner 2026-10-31); use the corresponding `/loki/api/v1` routes. No other write endpoint is planned.

| Read API signal | Registry evidence |
|---|---|
| Routed endpoints | 25/27 |
| Endpoints with Loki differential tests | 19/27 |
| Endpoints declared `proven` | 12/27 |

Routing, linked tests and declared proof are different signals; none means
every LogQL shape or every backend version is compatible. See the
[coverage map](compatibility-coverage.md) and [ranked differences](https://github.com/ReliablyObserve/loki-vl-proxy/blob/main/conformance/reports/parity-gaps.md).

Read routes without an implementation:

| Route | Current scope |
|---|---|
| `/loki/api/v1/cache/generation_numbers` | Not implemented |
| `/loki/api/v1/index/shards` | Optional planner gap; low priority, counted in scores |

`index/shards` is not required by the pinned Grafana/Drilldown request paths
or by proxy peer-cache lookup.

`cache/generation_numbers` is not implemented; manual cache flush and
eviction do not provide a distributed deletion generation.

**Alerting is not finished.** The proxy does not evaluate alerting or recording rules and
does not implement Loki's ruler API. What ships today is a read bridge: the rules routes
(`/loki/api/v1/rules`, `/api/prom/rules`, `/prometheus/api/v1/rules`, with namespace and
group lookups) and the alerts routes pass reads through to a vmalert configured with
`-ruler-backend` / `-alerts-backend`, and vmalert evaluates its own rules against
VictoriaLogs. Everything beyond that bridge (Loki-compatible rule evaluation, rule writes and
full ruler parity) is planned work, not shipped.

| Area | Current state |
|---|---|
| Write path | Out of scope by design: the proxy is read-only, so `POST /loki/api/v1/push` stays blocked. Ingest goes to VictoriaLogs directly, through its own ingestion paths. |
| Delete path | By default `/loki/api/v1/delete` is not registered and answers `404`, as Loki does with deletion disabled. With `-delete-api-enabled=true` (which requires `-delete-api-auth-token`; every delete request must carry the token) a create request runs as a VictoriaLogs delete task and a cancel stops the tenant's running task, with Loki's answers. Not served: the list of requests (GET) and a query whose rows a VictoriaLogs filter cannot select (a parser such as `| json`, a filter on a parsed label) answer Loki's `500`, deletion starts at once instead of after Loki's cancellation period, and answers cached before a delete keep serving the deleted rows until they expire. See [Security hardening migration](security-hardening-migration.md#remaining-delete-api-gap). |
| Rules and alerts lifecycle | Read compatibility is exposed through Loki YAML and Prometheus-style JSON views when `-ruler-backend` / `-alerts-backend` is configured. Rule writes and alert lifecycle changes remain outside the proxy, and alerting is not production-ready: Loki-style alerting and recording rules are the next big area, started once the query path is 100% ready ([roadmap](roadmap.md)). In `-tenant-label` mode an org sees only the rules and alerts labeled `<tenant-label>=<org>`. |
| Browser-origin tailing | `/loki/api/v1/tail` rejects browser `Origin` headers unless allowlisted with `-tail.allowed-origins`. |
| Multi-tenant tailing | Tail remains intentionally single-tenant. Loki-style multi-tenant tail fanout is not supported there. |

## Current Behavioral Differences

| Area | What to expect |
|---|---|
| Label vs field surfaces | With `-label-style=underscores` and `-metadata-field-mode=hybrid`, label APIs remain Loki-safe (`service_name`) while field-oriented APIs can expose both `service.name` and `service_name`. This is expected compatibility behavior, not duplicate data corruption. |
| Grafana dotted-field builder UX | Grafana builder paths can still tokenize dotted field names awkwardly even when the generated query executes correctly. For click-to-filter flows, underscore aliases are the safer UI path. |
| Parsed-only field freshness | `detected_fields` and `detected_field/{name}/values` prefer native VictoriaLogs metadata when possible, but parsed-only or very new fields can still fall back to bounded sampling. That means freshness can differ from indexed metadata. |
| Multi-tenant Drilldown aggregation | Multi-tenant `detected_fields` and `detected_labels` count the exact union of the values each tenant returns; when a tenant reports a larger cardinality than the values it returned, that count is used as a floor, so a merged cardinality can undercount the true cross-tenant union. |
| Wildcard tenant shorthand | `X-Scope-OrgID: *` is not a Loki-compatible all-tenants shorthand. An unmapped `*` returns HTTP 403 in both native and label-routing tenant modes unless `-tenant.allow-global=true` is set; an explicit tenant-map entry for `*` still takes precedence. In label-routing mode the default aliases (`0`, `fake`, `default`) and an empty org follow the same rule, except that no map entry admits an empty org. |
| Numeric tenant IDs | Tenancy is off by default: `X-Scope-OrgID` is ignored and everyone reads account `0:0`, as Loki with `auth_enabled: false`. With tenancy on and numeric passthrough (`-tenant.numeric-passthrough=true`, or left unset next to another tenant setting), a numeric `X-Scope-OrgID` routes to the account of that number only in its canonical spelling (decimal digits, no sign, no leading zero, at most 4294967295), because Loki treats `7` and `007` as two tenants and VictoriaLogs has one account per number. `007`, `00`, `-1` and larger values get HTTP 403 `unknown tenant` unless the tenant map lists that exact string (`+7` gets Loki's own `400`). An explicit `-tenant.numeric-passthrough=false` next to a tenant map serves only mapped orgs. See [Tenancy and authentication](tenancy-and-auth.md#numeric-tenants-and-strict-routing). |
| Metric series of `| json` / `| logfmt` pipelines | Loki names a metric series with the stream labels plus every label the pipeline extracted, so `count_over_time({app="x"} \| logfmt [1m])` returns one series per distinct set of parsed values (450 on a 30-stream minute of the e2e generator, 1050 for `\| json` on a busier app) where the proxy returns one per stream (30). The key set of those two parsers is known only once a line is read, so matching Loki means evaluating the query from rows instead of pushing it down to VictoriaLogs stats, which the proxy does not do by default on wide ranges. `-exact-parser-series-identity=true` opts in per deployment. `| regexp` and `| pattern` name their captures in the query, so those labels are always part of the series identity and are grouped in VictoriaLogs. |
| Metric series after an extraction list | After a parser that names its keys (`\| logfmt amount, route`, `\| json amount`) a Loki series is the stream plus the listed labels, less the unwrapped one. `sum`, `max`, `min` and `avg` over `avg_over_time`, `max_over_time`, `min_over_time`, `stddev_over_time` and `stdvar_over_time` read those series on an instant query and on a range up to the step, grouped in VictoriaLogs. Still read per stream or per line: `count` over the series; `first`, `last`, `quantile`, `rate` and `rate_counter` under an aggregation; a json alias or path in the list; a ranking, `sort` or grouping by a listed label; a range longer than the step (`semantics/unwrap-extraction-list-series-identity`, `semantics/unwrap-per-series-identity-raw-rows`). A line without a listed key carries no label where Loki keeps it empty (`semantics/extraction-list-empty-label`), and a value the unwrap cannot convert after a list answers 200 where Loki answers 400 (`semantics/unwrap-extraction-list-conversion-error`). |
| Line keys no stage exposed, in metric queries | In the Loki-compatible profile a log query reports only the labels its stages add (an extraction list, captures, `label_format` targets; nothing for `line_format`) and a label filter on a JSON line key no earlier stage exposes drops the row, as Loki does; a page is refilled from further rows, at most `-label-filter-refill-max-pages` (default 8; 0 = none) more requests of `limit` rows each, so a window with more dropped rows than that can answer with fewer lines than the limit. A metric query still counts such rows (`count_over_time({app="x"} \| user="u1" [5m])` is empty on Loki) and still groups by such a key (`sum by (user) (count_over_time({app="x"} [5m]))`), and a filter that accepts an empty value (`\| user!="u1"`) still misses rows whose stored key fails it. Telling a line key from structured metadata needs the stored line, which VictoriaLogs would have to read and parse for every row of the metric. |
| Lexer corners left to the proxy's own reading | Number, duration and bytes literals, keywords, single characters, NUL and a binary operator after a label filter follow Loki's lexer (see [LogQL parser](logql-parser.md#lexical-rules-of-lokis-lexer)). Still read differently: a range of a bare `0` (Loki accepts it), a range holding a Grafana variable (`[$__auto]`, the proxy's own error), a byte order mark at the start of a query, a stage that is a bare name alone (`\| x`) passes through to the backend as an unknown stage (a name followed by more of the stage, `\| x+y=1` or `\| a, b`, is Loki's 400), an unclosed stream selector after a binary operator (`{app="a"} + {`) keeps a generic error, and a negative `quantile_over_time` parameter or `topk(-5, ...)` keep their own messages. |
| JSON lines pushed without `_msg` | VictoriaLogs' Loki push endpoint stores a JSON line pushed without a `_msg` key as fields only (nested objects as dotted names, numbers as strings) with `_msg` set to its missing-message text. The proxy rebuilds the line from every stored field, structured metadata included, and cannot tell the line's keys from structured metadata, so those rows keep listing every field (structured metadata without a parser, parsed labels after `\| json` or `\| logfmt`). Push with `/insert/loki/api/v1/push?disable_message_parsing=1` to keep the original line; every field-exposure rule then applies (the supported setup). Where such pushes already exist and carry no structured metadata, `-json-line-fields-as-line-keys` (off by default) reads every stored field of a placeholder row as a key of its JSON line: no label until `\| json`, none from `\| logfmt`, and a query that unwraps or filters a label no stage can give such a line (after `\| logfmt` or without a parser) leaves those rows out, as Loki does; `\| json` metrics read such a row as a valid JSON object. With the flag on, structured metadata pushed beside such a line is hidden (VictoriaLogs stores it among the line's keys), as are the fields of jsonline rows and OpenTelemetry map bodies stored without a message; the flag needs a non-empty VictoriaLogs `-defaultMsgValue` and acts in the Loki-compatible profile only; a JSON value holding ` key=value` text, which Loki's `\| logfmt` reads from the line, is not read, and such a line is left out of a query the flag restricts; and these still read what VictoriaLogs stored: line filters (`\|=`, `\|~`) match the placeholder, a label filter an empty value passes before any parser reads the stored field, `\| logfmt` groups such a line by its stored fields where Loki groups it under empty values, and the line's number types, nesting and key order are lost. |
| Unwrap over a field stored as whole numbers | A plain `\| unwrap` (no parser) of a field VictoriaLogs stores with the line, such as structured metadata, reads no row of the blocks where the field's values are all whole numbers: VictoriaLogs keeps such a column as integers, and the regular expression the proxy classifies values with in a pipe's `if` condition matches none of its rows (v1.49 and v1.53). Those lines make no sample. A value a parser extracts is read. Tracked as `semantics/unwrap-stored-integer-field-gate`. |
| `last_over_time` on VictoriaLogs v1.49 | On v1.49 `last_over_time` with `\| unwrap` can answer an earlier line's value: VictoriaLogs' `row_max(_time, ...)` there takes the first row of a block whose group keys are all the same, which depends on how the store laid out its blocks. Fixed in VictoriaLogs v1.50.0. Tracked as `semantics/last-over-time-vl149-row-max-wrong-row`. |
| `first_over_time` / `last_over_time` over a series per line | With a range longer than the step, `first_over_time` and `last_over_time` over a parser with no `keep` after it (each line with a key of its own is a series in Loki) still read one step per point, not the window. With a `keep` before the unwrap, without a parser, or grouped by labels, they answer Loki's window. Tracked as `semantics/unwrap-first-last-per-line-range-longer-than-step`. |
| Metric range windows served from kept buckets | Metric `query_range` reuses the VictoriaLogs stats buckets it has read (`-query-range-extent-cache`, default on), as Loki's results cache does. Finished buckets older than `-query-range-freshness` (10m) are kept for `-query-range-extent-cache-ttl` (1h), so a line that arrives late in such a bucket is not seen until the kept bucket expires. Answers are byte-for-byte those of the uncached path. The window evaluator's answers, `topk` and `bottomk` over them included, are kept per evaluation time with the same rules (settled steps). The VictoriaLogs reads of subquery-based shapes, `_time:` and `time_add` queries and the `topk` and `bottomk` recurrence grids are not reused and recompute on every window (#862). A window whose start moves by less than its step (off the grid of the earlier windows) reuses neither buckets nor steps. |
| Query statistics (`data.stats`) | By default (`-query-stats-mode=loki`) the proxy emulates Loki's numbers (see [API reference](api-reference.md#query-statistics-datastats)): Loki's splits and shards; the lines of the 1h pieces Loki reads, which a log query that fills its limit stops after; bytes as lines times the mean line size. Where they differ from Loki: a log query that fills its limit reports the lines of the whole pieces it read, capped at the window's lines when the panel's count answer is held and at its entries times the pieces read otherwise, while Loki's figure depends on its chunk layout (on the test stack Loki reported 1,400 lines for 1,000 entries of a window of 3,174); `-query-stats-exact-log-lines` makes "whole pieces" exact with one VictoriaLogs count per log query miss; a filtered log query with no count of its bare selector reports its post-filter lines as lines; Loki counts every line of the blocks it opens, so on a sparse stream whose block holds lines outside the window Loki reports more lines than the window holds (24 for a 5m window of 18 lines on the test stack), while the proxy reports the window's lines; bytes are the bytes of the lines read, which for a log answer under its limit equal the bytes of the lines Loki returns; Loki's own total adds its structured-metadata bytes and, for data it reads from chunks, more per entry, both depending on its block layout (for one `detected_level`: 8 bytes a line on a steady stream, about 50 on a small fixture) and a metric query's bytes are estimated (exact with `-query-stats-exact-metric-bytes`, one extra VictoriaLogs volume request per metric query): from the log answer of the same expression over its window when held (its bytes exactly, the lines it does not cover at its mean line size), else from the mean line size of the selector's last log answer; the one-range lookback before a metric query's start is never covered by a log answer, so on a sparse stream whose lines differ in size from one minute to the next the estimate can be off by the difference (39% low in one CI case); Loki reads only part of a piece already in its store when a forward query starts there, the proxy counts it whole; a log query's `shards` are the 1h pieces it ran: every piece it read on the first answer of a query text, only the pieces that hold a returned entry on its repeat, both as Loki reports them; Loki also skips the pieces it found empty for the same text in an earlier request, so a text Loki already ran over another window, limit or direction (a refresh that slides the window by a minute, Drilldown changing the limit) reports fewer `shards` than the proxy's first answer, the proxy keeping no memory of pieces seen empty; `ingester` and `index` are always in Loki's zero form, so Grafana's "Ingester:" rows read 0. `-query-stats-mode=victorialogs` reports what the proxy measured instead. |
| Patterns surface | `/loki/api/v1/patterns` is optional (`-patterns-enabled`) and responses are clamped to `1000` patterns per request. |
| `count_values()` aggregation | Not part of LogQL: Loki v3.7.7 has no such vector aggregation and answers HTTP 400 `parse error at line 1, col 1: syntax error: unexpected IDENTIFIER` (the position is that of the name). The proxy answers the same message with `bad_data`, before any backend call. |
| Implicit many-to-one binary matching | Vector-vector operations where several series on one side match one series on the other without `group_left`/`group_right` are rejected with HTTP 500 and Loki's `multiple matches for labels` error. Cardinality is checked independently at each timestamp. |
| Window-dependent pipeline build errors | Loki reports a pipeline stage it refuses to build (an invalid `\| json`/`\| logfmt` extraction expression, a `label_format`/`line_format` template, a line filter regex or pattern, an `ip()` argument) with HTTP 400 over a window that ends within about two and a half hours of now, whatever the window holds, but with HTTP 200 and an empty result over an older window it holds no line for. The proxy answers Loki's 400 message over any window, after Loki's other checks: the request parameters and limits, the instant query type, the parser's checks and the checks over the parsed tree. The other errors (`\| pattern`, `\| regexp`, selector and label filter regexes, `topk(0, …)`, a range aggregation's grouping or unwrap) are 400 over any window on both. |
| `ip()` filter validation | An invalid address, prefix or range, or an operator other than `\|=`/`!=`, in an `ip()` line filter, and an invalid pattern in a label filter stage that is one `ip()` comparison (`\| addr=ip("zzz")`), answer Loki's 400 with Loki's text, for log and metric queries. A stage that joins several filters (`a="1", addr=ip("zzz")`) is accepted, as in Loki. Loki can skip building an invalid pipeline for an empty historical range; the proxy rejects the expression regardless of data. |
| Numeric label filters | After a `json` or `logfmt` parser, `\| m=5`, `\| m==5` and `\| m!=5` compare the value as a number, as Loki does: values Loki does not read in the literal's kind (a size or a duration where a number is asked, hexadecimal, binary or octal integers) are not taken for the number, and the spellings Loki reads in units VictoriaLogs does not read (`1kb`, `1 KB`, `5000000us`) are. Still different: a present but empty json value under `!=` (Loki keeps the line with `__error__`, the proxy drops it), a duration of several units spelled with `us` or `μs`, a size or duration with more fraction digits than its value needs, and a query that also compares with a signed number (text comparison). Before any parser they compare the value as text (`5.0` is not 5), where Loki compares it as a number (`5`, `5.0`, `05`, `+5` and `5e0` are all 5). Under any numeric filter (`>`, `>=`, `<`, `<=`, durations, bytes) a value that is not a number drops the line, where Loki keeps it with `__error__=LabelFilterErr`. |
| `ip()` matching precision | IPv4 patterns (an address, a CIDR of any length, a range) match like Loki's scan, as a line filter and as a label filter, including an address inside other text (`"10.0.0.5:443"`, `"client 10.0.0.5"`); the label filter is `ipv4_range` on a block VictoriaLogs stores as addresses and the exact regexp on a block that holds text. IPv6 patterns are still approximate: Loki's scan reads every spelling of an address (case, zero padding, `::` placement) and depends on the characters around it, and VictoriaLogs has no filter that scans for an IPv6 address. The label filter keeps the whole-address `ipv6_range` forms (a subset of Loki's lines, never a line Loki drops; an address inside other text or with a zone is left out under `=` and under `!=`); the line filter is a prefix regexp. An exact IPv6 regexp was built and proven against `ParseAddr`, and costs 7 to 50 times what today's forms cost on VictoriaLogs, so it is not shipped (semantics/ip-filter-precision). |
| Grafana query-split residual chunk | For Drilldown-tagged metric range requests shorter than one step (the trailing chunk of Grafana's 24h query splitting), the proxy returns an empty matrix with `X-Proxy-Drilldown-Path: hits-leftover-suppressed`. |
| Drilldown breakdown over the series limit | Above the tenant's `max_query_series` a Logs Drilldown label or field breakdown gets that many series with Loki's partial-result warning, cut as deployed Loki cuts it by default (`-drilldown-series-limit-mode=loki`: per split of `-drilldown-series-limit-split-interval`, Loki's `split_queries_by_interval`, the series met first, ending at the step where the series met so far pass the limit). Loki orders the series new in one step at random, so among those the kept set can differ from Loki's; every kept point has Loki's value. Loki's results cache can add the cut points of earlier requests' cached extents, which the proxy cannot know. `-drilldown-series-limit-mode=busiest` keeps the busiest series over the whole range instead. |
| Volume bytes and structured metadata | `/index/volume` and `/index/volume_range` report bytes like Loki, but the proxy counts exact log line bytes (VictoriaLogs `sum_len(_msg)`). Loki's volume is its chunk size estimate, which also counts structured metadata: 8 bytes for each structured-metadata name/value pair on every line (one `detected_level` pair per line when `discover_log_levels` is on) plus the metadata names and values once per chunk. Loki also splits a chunk's size across buckets by the share of the chunk's time span that falls into each bucket. For data still in the ingester, expect Loki to be higher by about 8 bytes per line per metadata pair, give or take about one line per stream per bucket. Once chunks are flushed, Loki rounds each chunk to whole KiB and adds a chunk once for every TSDB index file that lists it, so Loki can report a multiple of the stored bytes until its index files are compacted. Labels, timestamps, result type and ordering match Loki for single-tenant requests. |
| Volume extensions and multi-tenant volume | `targetLabels=detected_level` returns per-level volumes from the log lines (lines without a level form a `detected_level=""` volume); Loki keeps `detected_level` in structured metadata and returns no volume for it. Multi-tenant volume requests return each tenant's volumes with a `__tenant_id__` label, up to `limit` per tenant, in tenant order; Loki sums volumes of the same name across tenants, applies `limit` once and orders by volume. |
| Near-now label freshness | Loki lists labels and label values from its index and ingesters, so a stream written a moment ago is listed at once. The proxy reads the near-now edge from VictoriaLogs. When that read does not finish within `-metadata-edge-refresh-budget` (100ms), a `/labels` or `/label/{name}/values` request ending near now is answered from the last answer this replica read for the same tenant and window, at most `-metadata-max-staleness` (10s) old. Such an answer carries `X-Proxy-Stale-Response: true`, and the next request lists what the background refresh found. Requests ending more than `-max-metadata-cache-freshness` ago, and `/series`, are always exact. `-metadata-max-staleness=0` restores exact answers that wait for VictoriaLogs. |
| Metadata default lookback | `/labels`, `/label/{name}/values` and `/series` requests without `start`/`end` are bounded to the last 12h (`-metadata-default-lookback`; `0` disables). |
| Log stream `detected_level` | Log query responses, tail, `/patterns` and `/detected_fields` derive `detected_level` from the stored row with Loki's rules (stored `detected_level`, stream and other level fields, `severity_number`, then the JSON, logfmt and keyword reading of the line, `unknown` otherwise), in the stream labels by default and as structured metadata with `categorize-labels`. Remaining differences come from what VictoriaLogs stores: a JSON line that VictoriaLogs unpacked into fields (Loki push API without `disable_message_parsing=1`) has lost its key order and `null` values, so a nested level key listed before a top-level one, or a keyword that appeared only as a `null` key, can resolve differently. Rows written with a JSON key as the message field (`_msg_field`) keep their other keys as stored fields, so an unknown level word such as `notice` is kept where Loki would scan the line. A level field created at query time by `\| json`, `\| logfmt` or `\| label_format` is read like a stored field, and `\| drop` or `\| keep` stages that remove stored level fields change the derived value, while Loki's is fixed at ingest. With the default encoding only `level` and `detected_level` join the stream labels, not other structured metadata. An OTLP exporter that sends a `severity_text` identical to VictoriaLogs' form of the number (for example `Info2`) gets the level of the number. A stream selector matcher on `detected_level` treats the label as absent, as Loki does for structured metadata, unless `-stream-fields` lists `detected_level`; a `detected_level` label pushed as a Loki stream label is an index label in Loki, so list it there to select on it. `by (detected_level)` metric grouping derives the same value, computed by VictoriaLogs over the same stats query, so a grouped metric query and a log response agree, except for a row with a stored `log.level` field: Loki stores such structured metadata as `log_level` and reads no level from it, as log responses do, while the grouping still reads it (`severity/stored-log-dot-level-in-metric-chain`). `\| detected_level` filters and volume by `detected_level` still do not read the line: they use the stored `detected_level` or `level` field. |
| JSON and logfmt parser errors | A metric whose `\| json` parser meets a line it cannot parse fails with Loki's HTTP 400 `pipeline error: 'JSONParserErr' for series: ...` text under every function Loki keeps the error through (`sort`, `topk`, `label_replace`, aggregations, binary and set operations, offsets), detected in the metric's own VictoriaLogs reads; a `sum` without grouping of `rate` or `count_over_time`, `absent_over_time`, a `__error__` filter and `drop __error__` answer as in Loki. Which failing series Loki names changes from one run of a query to the next; the proxy names the earliest failing line it finds. Not detected (HTTP 200 where Loki fails): `\| logfmt --strict` syntax errors, a JSON pipeline outside the ordered evaluator's supported subset (for example, `line_format` or an unsupported second-parser pipeline), and, under `sort` or `topk`, lines both parsers read as JSON while Loki's rejects them (a value `NaN`, `.5` or `+1`, an invalid escape in a key). `sort` over a range aggregation whose pipeline ends in `keep` (`sort(count_over_time({…} \| json \| keep a, b [1m]))`) is sent to VictoriaLogs as a log query: a `streams` answer or HTTP 500 on `query_range`, HTTP 400 on an instant query. |
| Sequential JSON and logfmt | Eligible grouped count/rate/byte metrics evaluate both bare parsers in order, as do supported original trailing-keep ranges. The explicit JSON subset is one top-level key under its own name, followed by logfmt, an unconditional drop of both error labels, and the same key's nonempty filter. Supported wrappers preserve inner errors and matrix order. Log replies, malformed strict logfmt and other unsupported pipelines can still use sampled parser selection. Raw evaluation retains its row/byte limits and can cost more than native stats; see [ordered parser coverage](real-window-compatibility-gaps.md#ordered-json-and-logfmt-metrics) and registry `semantics/two-parsers-keep-one`. |
| Ranking over a per-stream aggregation on `query_range` | A `topk` or `bottomk` over a `max`, `min`, `avg` or `count` by labels (`bottomk(5, max by (env) (count_over_time({app="api"}[1h])))`) on `query_range` ranks the series of each stream, with their stream labels, instead of the groups of the aggregation, when the range is shorter or longer than the step; the instant query answers as Loki (registry `semantics/rank-over-stream-first-aggregation-range`). |
| `unwrap` conversion errors | A value the unwrap conversion rejects fails the query with Loki's HTTP 400 `pipeline error: 'SampleExtractionErr' for series: ...` text, detected in the metric's own VictoriaLogs stats scan. Not detected (HTTP 200 without the rows that do not convert, where Loki may fail): a filter after the unwrap that keeps only the error (`__error__!=""`) or compares a label (`v > 3`), an `and`/`or` filter expression, `label_join` around the metric, an `and`/`or` set operation whose other operand reads a clean stream, a value Loki rejects hidden by a later duplicate logfmt key (`v=abc v=5`; VictoriaLogs keeps the last value, Loki the first), a stored structured-metadata value hidden by a parsed key of the same name, values whose conversion overflows (`1e309`), and pipelines with `pattern`, `json`/`logfmt` arguments or a `label_format` writing the unwrapped label. Rows VictoriaLogs' parser rejects but Loki's converts (`v=5 v=abc`, `5KB` followed by U+FFFD) answer 200 like Loki without their samples. Which failing line Loki names depends on its shards; the proxy names the first line VictoriaLogs returns. |
| Live tail latency | A native or `auto` tail (`-tail.mode`) shows a line about 5 s after it is written; Loki's tail shows it within a second. VictoriaLogs makes a row searchable only when its in-memory buffer flushes, and its live tail never sends an earlier row of a stream after a later one, so the proxy reads rows at least `-tail.settle-delay` old (5 s by default, VictoriaLogs' default tail offset) to deliver every line. A shorter delay lowers the latency and can lose lines (1-2 s covers one single-node buffer flush only). The polled tail (`-tail.mode=synthetic`) keeps its 2 s poll latency. |
| OTel attribute translation in upstream queries | By default (`-translate-otel-attributes=true`), the LogQL→LogsQL translator rewrites known OTel semantic convention labels from underscore to dotted form (e.g., `k8s_container_name` → `k8s.container.name`). Deployments that store these fields with underscores (Vector, Promtail, Fluent-bit via Elasticsearch bulk ingest) should set `-translate-otel-attributes=false`. |

## Translation and Performance Caveats

Some compatibility behavior is implemented in the proxy rather than delegated to
native VictoriaLogs primitives. That keeps the Loki-facing contract usable, but
it also means latency, CPU cost, and observability differ from a native Loki
backend or a pure VictoriaLogs query path.

This especially matters for:

- parser and filter compatibility stages
- some response shaping and label/field alias resolution
- parts of binary compatibility behavior
- formatting helpers such as `line_format` / `label_format`
- unwrap helper compatibility such as duration and byte parsing

Treat those paths as supported compatibility work, not as zero-cost backend
equivalents.

### Where the proxy is slower than Loki

The current counts, slowest query shapes and answer differences are generated
from retained A/B runs in the [generated quality summary](real-window-compatibility-gaps.md#quality-and-performance-vs-loki-current),
[performance report](https://github.com/ReliablyObserve/loki-vl-proxy/blob/main/conformance/reports/performance.md)
and [ranked parity gaps](https://github.com/ReliablyObserve/loki-vl-proxy/blob/main/conformance/reports/parity-gaps.md).
First request, repeat and refresh are separate measurements; the historical
above-2× list also retains rows awaiting its consecutive-pass rule. An exact
repeat improvement does not establish shifted-window or peer-loss performance.
These reports retain the measured revision and date, rather than treating older
measurements as timings for the current tree.

### Hot+Cold response merging

When both hot (VictoriaLogs) and cold (Victoria Lakehouse) backends return results,
the proxy merges them in a streaming fashion. Backward-direction queries use a
bounded ring buffer (`maxRingSize=5000` entries) for the reverse pass rather than
materializing the full cold response. Very large time ranges hitting both backends
will still see higher proxy memory usage than hot-only queries, but the ring buffer
caps the worst case.

## Operational Caveats

| Area | Current state |
|---|---|
| Patterns persistence | If `-patterns-persist-path` is configured and not writable, startup fails fast. Without persistence, the endpoint still works, but warm state is lost on restart. |
| Label-values persistence | If `-label-values-index-persist-path` is configured and not writable, startup fails fast. Without persistence, indexed browse state is rebuilt after restart. |
| Startup warm readiness | When patterns or label-values startup warm is configured, readiness can remain `503` until disk restore or peer warm completes. |
| Older VictoriaLogs metadata paths | Newer VictoriaLogs versions let the proxy prefer stream-only metadata APIs. Older versions may fall back to broader field APIs, which can change how strictly stream-shaped some browse endpoints feel. |
| VictoriaLogs before v1.54.0 | Read with VictoriaLogs v1.54.0 or later where many log lines share a timestamp or a cluster runs with `-search.allowPartialResponse`: before v1.54.0 a log read with a limit could miss or repeat lines of one timestamp, and `vlselect` could return an incomplete answer without an error when a storage node failed, which the proxy cannot tell from a complete one (registry `vl-limit-read-timestamp-ties`). On v1.54.0 a live tail matching more than 10,000 lines in one refresh is ended by VictoriaLogs; the proxy closes it with Loki's internal error where Loki keeps streaming (`semantics/tail-ends-on-vl-row-rate-limit`). |
| Large body fields | Very large body fields can still be dropped on the VictoriaLogs side. Track the upstream issue: [VictoriaLogs issue #91](https://github.com/VictoriaMetrics/victorialogs-datasource/issues/91). |
| Optional tenant header | By default tenancy is off and the header is ignored. With tenancy on, a request without `X-Scope-OrgID` reads the default tenant unless `-require-tenant-header` (or `-auth.enabled`) is set, which answers Loki's `401 no org id`. |
| Execution limits | Bounded work limits reject oversized queries instead of truncating them: raw metric scans beyond `-manual-range-metric-row-limit` (default 1,000,000 rows) return an explicit error (HTTP 400 `bad_data` with Loki's `limit reached while evaluating the query`; the log line names the flag) instead of a partial result; binary expressions are limited to 64 nesting levels, 1,024 child evaluations and shared memory/sample budgets; `line_format` to 64 KiB per line and 16 MiB per response (HTTP 400). See [Security hardening migration](security-hardening-migration.md#execution-and-storage-limits). A rejected query does not mean the logs are absent. |
| Metric series caps | A metric query above `-max-stats-query-series` (default 1000; Loki's own default `max_query_series` is 500, and the proxy's higher default is an intended difference: it answers faster than Loki, so it affords more series per query; set `-max-stats-query-series=500` to match Loki) fails with Loki's HTTP 400 `maximum number of series (N) reached for a single query` on every path, range and instant. Grafana Logs Drilldown receives a partial result with Loki's `... returning partial results` warning; it holds the busiest series by total count, where Loki keeps the first series it encounters. |
| Multi-tenant fanout concurrency | When `X-Scope-OrgID` contains multiple tenants, the proxy fans out sub-requests in parallel (goroutine per tenant). Latency equals the slowest tenant, not the sum. Very high fan-out (10+ tenants) may increase backend load proportionally. |


## What Is No Longer an Open Gap

These are not current open issues in this codebase:

- Client errors use Loki's status and text on every route, through one error layer: VictoriaLogs' status and text never reach a client (they go to the log line), the proxy's own wording (translator, plan, limits) is replaced by Loki's, and a failed backend call is classified by its error type, not its message (#1422, #1430). Grafana-sourced stats requests that VictoriaLogs fails now answer Loki's error status (500, 504, 499 or 429), not HTTP 200 with warnings.
- Limits and queues answer Loki's texts and statuses: the per-client rate limit and `-max-concurrent` answer `429 too many outstanding requests`; row, binary and fan-out limits answer `400 limit reached while evaluating the query`; buffered response limits answer Loki's `500 ... grpc: trying to send message larger than max`; the flag that set the limit is in the log line only (#1422).
- Request parameters are checked as Loki checks them, in Loki's order, before the cache or any VictoriaLogs call (`start`, `end`, `time`, `since`, `step`, `interval`, `limit`, `direction`, `delay_for`, form and URL decoding) (#1419); methods, paths and `format_query` answer as Loki's router does (#1417).
- Queries Loki rejects after parsing (`sort`/`sort_desc` with grouping, `quantile_over_time` without its parameter, set operations with a number operand, `label_replace` over a log query) are rejected with Loki's 400 before any VictoriaLogs call; a metric query over a zero range answers Loki's empty result (#1434).
- Alerts, rules and stats answers the proxy cannot pass on (malformed, truncated, an error under 200) fail with Loki's 500 instead of a 200 (#1433).
- `stddev_over_time` and `stdvar_over_time` over an unwrapped label match Loki when the range is not the step, and `topk`/`bottomk`/`sort`/`sort_desc` around a grouped `stdvar_over_time` answer 200 (#1437).
- `sum`, `max`, `min` and `avg` over a function taken per series of a label unwrapped after an extraction list (`| logfmt amount, route`) read Loki's series, the stream plus the listed labels, on an instant query and a range up to the step.
- A `| keep` before `| unwrap` decides the series of `first`, `last`, `quantile`, `stddev`, `stdvar` and the other unwrap range functions, as in Loki (#1445).
- POST metadata form identities — selectors and bounds in the effective form are included in the cache key with body precedence, without mutating the request form. Upgraded binaries fence earlier ambiguous metadata entries across memory, disk, peers and the outer GET cache. Equivalent forms share metadata entries; the outer GET cache remains path-specific. The [retained main/PR/Loki proof](https://github.com/ReliablyObserve/loki-vl-proxy/pull/949) covers selector isolation and exact reuse, not distributed deletion invalidation.
- read-path query and label fanout across multiple tenants
- Grafana Logs Drilldown contract coverage as a tracked compatibility product
- Loki-compatible `/loki/api/v1/patterns` support with persistence and peer warm
- route-aware proxy, cache, and upstream request telemetry
- prefixed app metrics under `loki_vl_proxy_*` with CI guard coverage
- `max`, `min`, `count` and `avg` over a range function on `query_range` — one series per group, as in Loki, where the proxy returned one series per stream when the window is not the step (#734)
- Default-disabled delete routing — answers `404` like Loki with deletion disabled and is registered only with `-delete-api-enabled` (#855). This fixes the route exposure boundary; since 2.330.0 an enabled delete API runs create and cancel as VictoriaLogs delete tasks, and what it does not serve is listed in the Delete path row above.
- `label_replace()` — fully implemented in translator with proxy-side post-processing (v1.21.0)
- `label_join()` and `group()` — not in Loki 3.7.7's LogQL; both are a 400 parse error like Loki's (they were proxy-only extensions from v1.21.0)
- bare label matcher malformed VL output — queries like `app="value"` (missing braces) now return a descriptive HTTP 400 instead of silently producing double-quoted VL syntax (v1.20.0)
- `detected_level` on log responses — derived per row from stored fields and the line with Loki's rules, including `unknown`, normalised values and structured metadata placement under `categorize-labels` (Unreleased; replaces the v1.20.0 JSON/logfmt inference)
- circuit breaker sliding window — failure counting uses a 30-second sliding window; sporadic slow-query resets no longer open the breaker (v1.18.0)
- deterministic log stream ordering for multi-window queries — streams and per-stream values now sorted stably before response emission (v1.21.1)
- `offset` directive — fully implemented: proxy strips the offset clause and shifts `start`/`end` (or `time` for instant queries) backward by the offset duration before backend dispatch
- `| drop field=value` matcher semantics — proxy now conditionally removes a field only when its value matches, via proxy-side post-processing (`ParseDropConditions` + `applyDropConditions`); previously the value predicate was silently ignored and the field was always dropped (v1.36.1)
- structuredMetadata vs parsedFields classification — proxy correctly classifies structured metadata fields by comparing against `_msg` JSON content; previously some structured metadata fields were misclassified as parsed fields (v1.36.0)
- `| keep field=value` matcher form on stream labels — proxy now applies keep conditions to stream labels (not just structured metadata / parsed fields); mirrors the existing `| drop field=value` stream label path (v1.51.0)
- Parallel multi-tenant fanout — sub-requests dispatched via goroutine-per-tenant with `sync.WaitGroup`; latency equals slowest tenant, not sum (v1.37.1)
- Streaming backward hot+cold merge — cold reverse pass uses bounded ring buffer (`maxRingSize=5000`) with early termination instead of full body buffering (v1.37.1)
- `absent_over_time()` — fully implemented (v1.35.0); translates to `stats count()` with empty-series emission
- `sort` / `sort_desc` outer aggregations — fixed in v1.35.0; sort by metric value across series now works correctly
- Cold storage backend routing (Victoria Lakehouse) — implemented v1.28.0; time-boundary split between hot VL and cold Lakehouse
