## Summary

Turns the findings from the manual compatibility pass against the latest Grafana 13.2 / Loki 3.7 / VictoriaLogs v1.52 / Logs Drilldown 2.5 stack into automated coverage, and repairs the parts of the e2e stack that could not run against either the newest or the oldest supported VictoriaLogs.

### e2e-compat stack
- **VictoriaLogs healthcheck** switched from `wget` to the binary's own `-version` probe. VictoriaLogs images are scratch-based from v1.52.0 (no shell, no wget), so the previous probe could never pass and every dependent container refused to start. HTTP readiness is still enforced by the proxies' health checks and `wait_e2e_stack.sh`.
- **Tuning flags moved to an override.** `-defaultParallelReaders` and `-fs.maxConcurrency` do not exist on VictoriaLogs < v1.34 / < v1.37 and an unknown flag exits the process at startup. That silently failed the weekly VL matrix for v1.30–v1.36 (`container e2e-victorialogs is unhealthy`). They now live in `docker-compose.bench.yml`, used by the benchmark harness only; `bench/README.md` and `docs/benchmarks.md` point at it.
- `compatibility-matrix.json` gains v1.51.0 and v1.52.0; `compat-vl.yaml` now runs the full matrix on `workflow_dispatch` too (the docs already said "scheduled and manual").
- The same `wget` probe lived in the root compose file, e2e-fleet, e2e-pipeline and every `examples/` compose file; the examples pin `victoria-logs:latest`, so the public quickstart could not start its proxy once `latest` moved to v1.52.0. All now probe the binary. The e2e log generator also waits for the main proxy (whose `/ready` probes VL `/health`) so its first batch is not lost on the VL side of the dual write.

### e2e-ui
- **Logs Drilldown 2.5.x selectors.** The "Filter by labels" / "Filter by fields" controls are located through `drilldownLabelFilter` / `drilldownFieldFilter` helpers. on Drilldown 2.5.x `getByRole("combobox", { name })` times out for them while `getByPlaceholder` resolves the same input (observed on 2.5.2), so every drilldown-core / drilldown-mt spec failed against the latest plugin while the proxy rendered the pages correctly.
- **`@regression` and `@comprehensive-ui` suites repaired and wired into CI** as the `explore-regression` and `explore-comprehensive` shards. They had never run in CI and had rotted: the comprehensive suite queried a `job` label the dataset does not carry; the regression suite compared windows ending at "now" (drift while the generator writes), asserted exact raw per-stream series counts that the proxy caps at `-max-stats-query-series` (500), and compared `limit`-capped line counts. Log parity now compares a two-minute, uncapped window (fails if empty or capped); metric parity uses bounded aggregations; volume comparisons use instant `count_over_time` aggregates; the series cap has its own describe over a 15-minute window. The comprehensive suite asserts a rendered graph for its (previously invalid) unwrap query, checks every test for Grafana errors, and records timings as annotations.
- **Proxy-vs-Loki metric comparisons account for Loki's fresh-stack behaviour.** On a freshly started stack Loki 3.x answers range metric queries with an empty 200 for the first minutes: the query-frontend's dynamic sharder sizes shards from index stats and the ingester reports no bytes for a stream until its head block is cut (`splits=1 shards=0 querier_exec_time=0s` in Loki's query log), after which streams become visible one at a time. Instant queries, log queries and the proxy return the data immediately, and because the UI generator rotates pod names the newest streams always lag on Loki's range path (measured on a 4-minute-old stack: proxy 437 series for 437 indexed streams, Loki `rate()` 417). CI runs the UI shards seconds after readiness. `waitForLokiMetricData` (modelled on the Go suite's helper, stricter: group completeness against Loki's series index, fails instead of warning, tolerates transient errors while polling) now gates grouped comparisons until Loki's range path reports every level/namespace group its own series index lists, and the series-cap test counts streams against Loki's series index (`lokiIndexedStreamCount`) instead of Loki's `rate()` output.
- **New regression locks** for behaviour verified by hand:
  - `drilldown-limits-gate.spec.ts` (@drilldown-core): the Patterns tab is hidden for the default proxy datasource and shown for the patterns-autodetect variant and for Loki, exactly as `drilldown-limits.pattern_ingester_enabled` dictates; the proxy's payload is a key-superset of Loki's.
  - `explore-parity.spec.ts` (@explore-core): `sum by (level) (rate({app="api-gateway"}[5m]))` yields the same series set from the proxy and from Loki through Grafana's datasource proxy.

## Independent review

The diff was reviewed by a separate reviewer pass (14 findings). Confirmed and fixed here: the remaining `Filter by fields` role selectors in the cache-regression suite; the invalid `unwrap ... | avg` query and unasserted guards in the comprehensive suite; `limit`-capped log parity; the 7-day per-stream query and series listing; no error tolerance in the warm-up poll and a memoised rejection; the `wget` probe in the examples and other compose files; stale shard/suite docs and the VictoriaLogs version-matrix rows; CHANGELOG wording; `toHaveProperty` dotted-key semantics and a `drilldown-limits` response wait in the gate spec; wall-clock assertions replaced by annotations; the fixme header claim. Declined: switching the fixme cases to `test.fail()` (they would execute known-broken queries on every run; the header now says what happens instead). Verified independently: rule compliance, CI wiring and tags, datasource wiring, cap semantics, compose override precedence, `wait_e2e_stack.sh`, the proxy's `/ready` probing VL.
